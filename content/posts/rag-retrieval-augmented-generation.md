## 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把信息检索与大模型生成结合起来的架构。传统大模型主要依赖训练阶段记忆的知识，可能遇到知识过时或生成幻觉的问题；RAG 则在生成回答前先从企业文档、论文、数据库或其他可靠来源中检索相关内容，再让模型基于这些内容作答。

RAG 不需要重新训练基础模型，而是通过更新外部知识库让回答及时跟随数据变化，并让回答有可追溯的事实依据。相当于给大模型增加了一个“实时查资料”的能力，让回答锚定在真实数据上。

## RAG 工作流程

RAG 通常分为两个阶段：离线构建知识库和在线检索生成。前两个步骤主要用于将相关知识库转换为向量并存储，为后续的检索增强提供基础。

1. 文档收集与切分；
2. 文本向量化并存储；
3. 将用户问题转换为查询并检索相关片段；
4. 组装增强提示词，由大模型生成回答。

### 1. 文档收集与切分

文档收集阶段从网页、数据库、PDF、Markdown 或企业系统等多种数据源收集原始数据；文档预处理阶段负责清洗原始文档并进行标准化、去重和权限标注；文档切割阶段再将文档切分成合适的片段，可以采用语义分割或固定大小分割。过长文档需要切分为大小适中的 Chunk，既要保证单块能表达完整语义，也要控制输入模型的 Token 数量。

常见切分方式包括固定长度切分、按标题/段落切分、按句子切分，以及带重叠窗口的语义切分。对于表格、代码和 FAQ，最好使用保留结构的专用切分器。

![文档收集、预处理与切分](../assets/posts/rag-retrieval-augmented-generation/document-pipeline.png)

### 2. 向量转换与存储

Embedding 模型把每个文本块映射为高维向量。语义相近的文本通常在向量空间中距离更近，然后将向量、原文、来源、时间和权限等元数据一起写入向量数据库。

![文本块向量化并写入向量数据库](../assets/posts/rag-retrieval-augmented-generation/embedding-storage.png)

![Embedding 存储流程示意](../assets/posts/rag-retrieval-augmented-generation/embedding-storage-detail.png)

向量数据库可以使用 PostgreSQL + pgvector、Milvus、Qdrant、Weaviate 等方案。选型时要考虑数据规模、过滤条件、部署成本、查询延迟和团队运维能力。

### 3. 文档检索

在线请求到达后，先使用同一个 Embedding 模型将用户问题转换为向量，再通过余弦相似度、点积或欧式距离召回候选文本块。为了减少“相似但不够准确”的结果，常见流程是先召回较大的候选集，再用 Rank 模型精排，最终保留 TopK 文档。

![用户问题向量化、相似度召回与精排](../assets/posts/rag-retrieval-augmented-generation/retrieval-ranking.png)

### 4. 提示词构建与生成

将用户问题、检索到的文档片段、来源信息和回答约束组装成增强提示词，再交给大模型生成最终答案。提示词应明确要求模型优先依据上下文回答，信息不足时说明无法确定，不要凭空补全。

![将问题与相关文档交给大模型生成回答](../assets/posts/rag-retrieval-augmented-generation/prompt-generation.png)

### 完整流程

```text
文档 → 清洗/切分 → Embedding → 向量数据库
                                      ↑
用户问题 → Embedding → 相似度召回 → 重排序 → TopK 文档
                                                    ↓
                            用户问题 + 文档上下文 → 大模型 → 回答
```

![RAG 完整检索增强生成流程](../assets/posts/rag-retrieval-augmented-generation/full-rag-flow.png)

## RAG 关键技术

### Embedding 技术

Embedding 的目标是把文本、关键词和问题映射为可比较的语义特征。模型选择要与场景匹配：细粒度领域检索需要更强的语义分辨力，粗粒度召回则可以采用轻量模型以降低延迟和成本。

关键技术细节包括：

- **向量的语义颗粒度**：如果需要细粒度匹配，例如区分“RAG 的检索步骤”和“RAG 的生成步骤”，应选择语义分辨力强的模型，如 BGE-large、`text-embedding-ada-002`；如果只是粗粒度召回，例如筛选 RAG 相关文档，M3E-base、Sentence-BERT 等轻量模型即可满足，推理速度也更快。
- **长文本 Embedding 的适配**：常规模型对超过 512 Token 的文本处理能力有限，可能发生截断或语义失真。可以先把长文本切分成子块（例如每块 200 Token），分别生成向量，再按子块与核心语义的关联度进行加权融合，或者先生成摘要，再对摘要进行 Embedding。
- **领域适配优化**：通用 Embedding 模型在医疗、法律等垂直领域可能出现语义偏移。例如“剂量”在医疗语境中指用药量，通用模型未必能准确理解。可以使用领域文本对等标注数据进行微调，使向量更贴合领域语义。

- **语义颗粒度**：Chunk 太小会丢失上下文，太大则可能包含多个主题，降低检索精度；
- **长文本限制**：超过模型上下文窗口的文本应先切分，不能依赖模型自动截断；
- **领域适配**：医疗、法律等专业领域可能需要领域数据微调或选择专业 Embedding 模型；
- **模型一致性**：写入知识库和查询时应使用兼容的 Embedding 模型及相同的预处理方式。

### 混合检索

混合检索的核心是通过向量检索抓语义关联、通过关键词检索抓字面匹配，弥补单一检索的缺陷。向量检索可能漏检关键词明确但语义表述特殊的内容，例如用户问“RAG 的 Chunking 步骤”，向量模型不一定强化了 Chunking 这个词；关键词检索则无法处理同义不同词，例如“文本分块方法”可能漏掉只出现 Chunking 的文档。

常用的是“关键词召回 + 向量精排”两步法：

1. 先使用 Elasticsearch 等传统搜索引擎的倒排索引，快速召回包含用户问题核心词的文本块；
2. 再对召回的文本块计算 Embedding 相似度并排序，保留 Top3～Top5 个最相关的块，过滤掉仅包含关键词但语义无关的内容。

例如，用户搜索 “文本分块方法” 时，关键词召回可以匹配“分块”，向量检索则可能补充包含 “Chunking” 的文档。

### 多轮检索

当首轮结果不足、信息碎片化或模型判断上下文无法回答时，可以触发第二轮检索。常见触发条件包括：检索召回率低（向量检索只召回一个相关块或关键词检索无结果）、检索结果信息碎片化（多个块各含部分信息但没有完整逻辑），以及生成回答模糊或存疑（模型判断基于现有信息无法明确回答）。

- **Query 改写**：补充时间、领域和限制条件，或将复杂问题拆成多个子问题；
- **检索范围调整**：从内部文档扩展到授权的外部来源，或限定时间范围和权威来源；
- **结合对话上下文**：将用户追问与历史问题合并，避免把“它”“这个方案”等指代词直接拿去检索；
- **结果反馈**：根据回答置信度、引用覆盖率或检索分数决定是否继续搜索。

例如，用户问“RAG 最近有什么新应用”，首轮结果可能集中在 2023 年案例；Query 可以改写为“2024-2025 年 RAG 在企业、医疗、教育领域的应用案例”，补充时间范围和领域。用户问“如何解决 RAG 的检索漏检”，则可以改写为“RAG 检索漏检原因及解决方案、RAG 混合检索与重排序优化方法”，扩大检索维度。

如果内部文档库检索无结果，可以在权限允许的前提下扩展到外部公开库；如果结果重复，则限定近六个月文档或权威来源文档。对于多轮对话，还应关联历史上下文：用户先问“RAG 需要向量数据库吗”，再追问“那用什么向量数据库好”，第二轮检索就应该优先召回 RAG 向量数据库选型和中小规模方案对比。

多轮检索会增加延迟和成本，因此应设置最大轮数，并记录每轮查询和召回结果便于排查。

### 知识增量更新

知识增量更新的目标是在不重建整个知识库的前提下纳入新文档、更新旧内容，避免旧数据冗余和新数据检索延迟。如果每次更新都重新分块、Embedding 和建索引，在百万级文档场景中会造成明显卡顿。更常见的增量方案是：

1. 为新增文档记录时间戳标签，例如“2025-08-28 新增”，再按常规流程切块和 Embedding；
2. 将新文本块的向量追加写入向量数据库，例如 Milvus 可以把新增数据写入独立分区，不影响存量分区检索；
3. 如果需要删除旧文档，可以按标签批量删除，例如删除“2023 年以前文档”，不必遍历整个数据库；
4. 同时记录版本、来源和权限信息，更新完成后切换版本标记，定期清理重复向量并优化索引。

文档删除必须同时处理向量、原文和缓存，不能只删除文件而保留可检索的向量。对知识库设置版本号，也有助于回答追溯和回滚。

## 实践注意事项

- **权限过滤**：检索前就应用租户、部门和文档权限，不能只依赖生成阶段隐藏内容；
- **引用来源**：将文档标题、URL、版本和页码作为元数据，方便回答展示出处；
- **防止提示词注入**：把检索内容视为不可信数据，明确区分系统指令和文档正文；
- **评估指标**：分别评估召回率、Precision@K、重排序质量、答案忠实度、引用覆盖率和端到端延迟；
- **上下文预算**：TopK 不是越大越好，过多片段会增加成本并引入噪声；
- **缓存与监控**：对稳定问题缓存 Embedding 和检索结果，同时记录查询、耗时、命中片段和模型回答。

## 小结

RAG 的核心不是简单地“把文档塞给大模型”，而是建立一条可维护的知识链路：高质量切分、稳定的 Embedding、合理的召回与重排序、受控的提示词，以及可追溯的增量更新。只有把检索质量、权限、安全和评估体系一起设计，RAG 才能在真实业务中稳定工作。
