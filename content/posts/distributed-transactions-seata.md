在分布式系统中，如果一个业务需要多个服务协作完成，并且每个服务都有自己的本地事务，那么这些事务就必须在整体上保持一致：要么全部成功，要么全部失败。这样的事务就是**分布式事务**。

解决分布式事务的关键，是让各个子事务能够感知彼此的状态，并由一个协调者统一做出提交或回滚决策。

## Seata 架构

Seata 中有三个重要角色：事务协调器（TC）、事务管理器（TM）和资源管理器（RM）。

![Seata 三大角色与调用关系](../assets/posts/distributed-transactions-seata/seata-architecture.png)

### TC：Transaction Coordinator，事务协调器

TC 维护全局事务的状态，协调全局事务的提交或回滚，并向各个 RM 发送分支事务处理指令。

### TM：Transaction Manager，事务管理器

TM 定义全局事务的范围，负责发起全局事务、提交全局事务或回滚全局事务。

### RM：Resource Manager，资源管理器

RM 管理分支事务和本地资源，与 TC 交互，负责注册分支事务、报告分支事务状态，并执行提交或回滚操作。

## Seata 的工作流程

1. **全局事务开始**：TM 向 TC 发起全局事务请求，TC 分配唯一的事务 ID（XID）。XID 会在后续服务调用中传播，用于标识同一个全局事务。
2. **分支事务注册**：各个服务中的 RM 感知到 XID 后，将本地业务操作注册为分支事务，并关联到对应的全局事务。
3. **业务执行**：各个 RM 按照业务逻辑执行本地分支事务，并记录执行过程所需的日志或快照信息。
4. **协调决策**：所有分支事务执行完成后，TM 根据业务结果向 TC 发起提交或回滚请求。若所有分支事务都成功，TC 发起全局提交；只要有一个分支事务失败，TC 就发起全局回滚。
5. **分支处理**：RM 收到 TC 的指令后提交本地事务，或根据记录的信息恢复本地数据，最终让整个全局事务达到一致状态。

## XA 模式

### 模式概述

XA 是由 X/Open 组织提出的分布式事务处理标准，依赖资源管理器提供的 XA 协议。在 Seata XA 模式中，数据库等 RM 通过两阶段提交参与全局事务。

### 工作流程

1. **全局事务开始**：TM 向 TC 发起请求，TC 分配 XID，TM 将 XID 传递给参与事务的业务服务。
2. **分支事务执行**：各个 RM 开启本地 XA 事务，执行具体的数据库操作。
3. **准备阶段（Prepare）**：TC 向所有 RM 发送准备指令。RM 将事务结果持久化，但暂不提交，并向 TC 报告准备成功或失败。
4. **提交或回滚阶段**：如果所有 RM 都准备成功，TC 向它们发送提交指令；如果任一 RM 准备失败，TC 向所有 RM 发送回滚指令。

### 优点

- **强一致性**：所有参与资源要么全部提交，要么全部回滚。
- **依赖数据库原生能力**：主流关系型数据库通常已经提供 XA 支持，不需要额外编写复杂的补偿逻辑。

### 缺点

- **性能开销较大**：两阶段提交需要多次网络交互。
- **资源锁定时间较长**：准备阶段到最终提交或回滚之间，资源可能持续被锁定，高并发时会影响吞吐量。

### 实现与适用场景

Seata 全局事务通常使用 `@GlobalTransactional` 注解开启。XA 更适合对一致性要求极高、数据库支持 XA 且并发量相对可控的场景，例如资金转账和结算系统。

## AT 模式

### 模式概述

AT（Automatic Transaction）是 Seata 提供的自动化、低侵入式分布式事务方案。它通过记录数据变更前后的镜像，在需要回滚时生成反向 SQL，恢复事务执行前的数据状态。

### 工作流程

#### 一阶段：执行业务 SQL

1. RM 在执行业务 SQL 前查询数据状态，生成 `before image`（前镜像）。
2. RM 执行业务 SQL，更新数据库中的业务数据。
3. 更新完成后再次查询数据，生成 `after image`（后镜像）。
4. RM 将前镜像、后镜像和业务 SQL 写入 `UNDO_LOG` 表，注册分支事务并向 TC 报告执行状态。

#### 二阶段：提交或回滚

- **全局提交**：TC 向 RM 发送提交指令，RM 异步删除对应的 `UNDO_LOG` 记录并释放资源锁。
- **全局回滚**：TC 向 RM 发送回滚指令，RM 根据 `UNDO_LOG` 中的前镜像和后镜像生成反向 SQL，将数据恢复到事务执行前的状态。

### 优点

- **低侵入性**：业务代码主要关注业务逻辑，无需手动编写复杂补偿流程。
- **性能较好**：一阶段完成业务数据和回滚日志写入，二阶段提交采用异步方式，减少锁定时间。
- **自动补偿**：回滚时由 RM 根据 `UNDO_LOG` 自动恢复数据。

### 缺点

- **依赖数据库能力**：需要数据库支持事务、行级锁以及相应的 SQL 解析能力。
- **需要关注隔离问题**：高并发场景下仍需结合业务设计处理脏读、幻读等数据隔离问题。

### 实现与适用场景

使用 `@GlobalTransactional` 开启 Seata 全局事务，并为参与事务的数据库准备 `UNDO_LOG` 表。AT 模式适合基于关系型数据库、业务逻辑相对清晰且对性能有要求的场景，例如电商系统中的订单创建和库存扣减。

## 小结

XA 依赖数据库原生的两阶段提交，强一致性更直接，但资源锁定和性能开销也更明显；AT 通过前后镜像和 `UNDO_LOG` 实现自动补偿，侵入性更低、性能更好，但对数据库能力和并发隔离提出了要求。

选择模式时，应结合数据一致性要求、数据库类型、并发规模和业务是否适合自动补偿来判断。
