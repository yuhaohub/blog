在并发编程中，最核心的两个问题是：线程之间如何通信，以及线程之间如何同步。

- **线程通信**：线程之间以什么机制交换信息；
- **线程同步**：如何控制不同线程操作共享数据的顺序。

Java 内存模型（JMM）正是理解这些问题的基础。

## JMM 抽象结构

JMM 是 Java 虚拟机定义的一种抽象内存模型，用来屏蔽不同硬件和操作系统的内存差异，并为并发程序提供可见性、有序性和原子性的保证边界。

![JMM 中线程、本地内存与主内存的关系](../assets/posts/java-concurrency-jmm/jmm-memory-model.png)

每个线程都有自己的工作内存，工作内存保存共享变量的副本。主内存保存共享变量的实际值，线程不能直接操作其他线程的工作内存。

### 线程 A 如何与线程 B 通信

线程之间没有直接访问对方工作内存的通道。以线程 A 修改变量、线程 B 读取变量为例，通常需要经过两个步骤：

1. 线程 A 将工作内存中更新后的变量刷新到主内存；
2. 线程 B 从主内存读取最新值，并更新自己的工作内存副本。

`volatile`、锁和 happens-before 规则可以影响刷新和读取的可见性，但它们解决问题的方式并不相同：`volatile` 主要提供可见性和一定的有序性，锁还会提供互斥和更强的同步语义。

## 重排序

重排序的主要目标是提高执行性能。只要不改变单线程程序的执行结果，编译器和处理器就可能调整指令顺序。

常见的重排序包括：

1. **编译器优化重排序**：编译器在生成指令序列时调整操作顺序；
2. **指令级并行重排序**：处理器利用多个执行单元并行执行指令；
3. **内存系统重排序**：处理器的缓存和写缓冲区导致读写操作呈现不同的可见顺序。

单线程中看似合理的代码，放入多线程环境后可能因为重排序和可见性问题产生不同结果。Java 会在生成指令序列时插入必要的内存屏障，限制不允许的重排序。

## 内存屏障

内存屏障是一类用于约束内存读写顺序的指令。常见的抽象类型包括：

![常见内存屏障类型](../assets/posts/java-concurrency-jmm/memory-barriers.png)

| 屏障类型 | 典型作用 |
| --- | --- |
| LoadLoad | 保证前面的 Load 数据装载先于后续 Load |
| StoreStore | 保证前面的 Store 数据刷新先于后续 Store |
| LoadStore | 保证前面的 Load 先于后续 Store |
| StoreLoad | 保证前面的 Store 对其他处理器可见后，再执行后续 Load |

不同 JVM、处理器架构和编译结果可能采用不同的底层指令实现。开发者通常不直接编写这些屏障，而是通过 `volatile`、锁和线程同步 API 使用它们提供的语义。

## happens-before

happens-before 不是代码执行时间上的“先发生”，而是一种用于描述内存可见性的规则：如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，并且 A 的执行顺序排在 B 之前。

![happens-before 规则示意](../assets/posts/java-concurrency-jmm/happens-before.png)

常见的 happens-before 关系包括：

- 同一个线程中，前面的操作 happens-before 后面的操作；
- 对一个锁的解锁 happens-before 随后的加锁；
- 对一个 `volatile` 变量的写 happens-before 后续对它的读；
- 线程的 `start()` 调用 happens-before 该线程中的操作；
- 线程中的所有操作 happens-before 其他线程观察到该线程终止；
- 如果 A happens-before B，B happens-before C，则 A happens-before C（传递性）。

编写并发代码时，应优先依赖这些明确的同步规则，而不是依赖某种处理器或当前 JVM 的偶然执行顺序。

## 数据依赖关系

如果两个操作访问同一个变量，并且其中至少一个是写操作，那么它们之间存在数据依赖关系。常见类型有：

- **写后读（RAW）**：后续读取依赖前一次写入的结果；
- **写后写（WAW）**：后一次写入可能覆盖前一次写入；
- **读后写（WAR）**：后续写入不能破坏前一次读取所需的数据。

在单线程中，编译器和处理器不会改变存在数据依赖的操作顺序，因为这样会改变程序结果。但这并不自动解决多线程之间的可见性和竞态问题，多线程仍需要使用同步机制建立明确的 happens-before 关系。

## 控制依赖关系

控制依赖来自条件判断。例如：

```java
if (flag) {
    // 操作 1
    a = i * i; // 操作 2
}
```

操作 2 是否执行取决于操作 1 的判断结果，因此两者之间存在控制依赖。控制依赖会限制指令级并行度，处理器可能采用猜测执行：提前读取并计算 `i * i`，暂存在重排序缓冲区中，待条件确认后再决定是否提交结果。

这说明“代码写在 if 里面”并不等于处理器在条件判断完成前绝对不会准备相关计算。真正需要保证跨线程顺序时，仍应使用 `volatile`、锁或其他同步原语建立内存语义。

## 如何把概念落到代码

下面的代码没有同步保护，线程 B 可能读取不到线程 A 更新的值：

```java
class Example {
    private boolean ready;
    private int value;

    void write() {
        value = 42;
        ready = true;
    }

    void read() {
        if (ready) {
            System.out.println(value);
        }
    }
}
```

如果将 `ready` 声明为 `volatile`，线程 A 对 `ready` 的写入就能对线程 B 可见，并建立相应的有序性：

```java
private volatile boolean ready;
```

如果需要保护多个变量的一致更新，则应该使用锁或其他能够提供互斥能力的同步方案，而不能只依赖 `volatile`。

## 总结

JMM 通过工作内存、主内存、重排序和 happens-before 规则，为 Java 并发程序定义了可见性与有序性的边界。理解这些概念后，可以更清楚地判断：什么时候需要 `volatile`，什么时候必须使用锁，以及为什么不能依赖单线程下看似自然的执行顺序。

并发代码的关键不是记住某条经验，而是为线程之间的通信和同步建立明确、可验证的内存语义。
